# M1.2 — Entity lifecycle and transactional outbox

## Delivered contracts

- `EntityLifecycleService.before()` applies module filters and then dispatches the matching before-action. A rejected filter or failed action prevents the caller from continuing.
- `recordWithinTransaction()` writes a versioned event envelope to `module_event_outbox` through the caller's TypeORM `EntityManager`.
- The outbox migration is registered under the existing migration glob and uses PostgreSQL `jsonb`, UUID event/correlation IDs, processing leases, and delivery status.
- `ModuleOutboxPublisherService.publishBatch()` claims rows with `FOR UPDATE SKIP LOCKED`, dispatches actions after the claim transaction commits, and marks success or schedules retry/final failure.
- Processing leases are reclaimed after five minutes if a worker exits unexpectedly.
- Delivery is at-least-once. A consumer must persist/deduplicate `eventId`; it must not assume exactly-once side effects.

## Transaction boundary (required)

The entity write and outbox insert must use the same transaction manager:

```ts
await dataSource.transaction(async (manager) => {
  const input = await lifecycle.before('insert', {
    moduleId: 'inventory',
    entityType: 'equipment',
    actorUserId,
    correlationId,
  }, createDto);

  const repository = manager.getRepository(EquipmentEntity);
  const entity = await repository.save(repository.create(input));

  await lifecycle.recordWithinTransaction(
    manager,
    'insert',
    {
      moduleId: 'inventory',
      entityType: 'equipment',
      entityId: entity.id,
      actorUserId,
      correlationId,
    },
    equipmentToEventSnapshot(entity),
  );
});
```

Do not use a globally injected repository for the write while passing a separate transaction manager to the outbox. Do not put ORM entities, repositories, or managers in event data; map an explicit, versioned DTO/snapshot. For deletes, capture the snapshot before deleting.

## Publisher operation

The publisher is exposed by `ModuleRuntimeModule`. A host worker/scheduler must call `publishBatch()` periodically; this change does not silently start a background timer in every API process. The method is safe to run from multiple workers because claims use row locks and skip rows claimed by another worker.

Handlers receive the full `EntityEvent` as their action payload. They should use `eventId` as an idempotency key. A crash after a consumer side effect but before marking the outbox row published can cause redelivery.

## Customer Branch integration boundary

The current Customer Branch creation flow saves Branch, provisions a login account, and then creates Staff, with compensating cleanup if a later step fails. It is not currently one database transaction and account provisioning may be external. Therefore, do not add `customer.branch.afterInsert` immediately after the initial Branch save. Publish a business-level `customer.branch.created` only after the complete workflow succeeds, or redesign the workflow around a transaction plus an explicit post-commit provisioning state/outbox command. The current lifecycle primitive intentionally requires the caller to choose and enforce the correct business transaction boundary.

## Operational notes

- Apply the new migration before enabling the publisher.
- Failed events return to `pending` until `maxAttempts` is reached, then move to `failed`; inspect and replay failed records through an explicit operator workflow.
- There is currently no automatic retry backoff or admin replay UI. Those are follow-up work, not implied by this API.
- Unit tests cover before filters/actions, transactional outbox insertion, publish completion, and retry behavior. Test execution still needs CI or a local checkout; a GitHub status response did not report a run.
